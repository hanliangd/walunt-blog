### 2026-10-05 · 忘了 `let` → 隐式全局变量，而且它**跨调用串**

**症状**：给 `streamChat` 加"断流检测"——收到 `[DONE]` 就置 `sawDone = true`，循环结束后 `if (!sawDone) onError(...)`。写完在浏览器里手动测：正常流（有 `[DONE]`）一切正常。但**真正断流时**（没有 `[DONE]`，比如 `uvicorn --reload` 中途重启）—— **`onError` 一次都没调用，静默什么都不发生。**

**根因**：`sawDone` **从来没声明过**。

```js
const parse = createParser((payload)=>{
    if (payload === '[DONE]'){
      sawDone = true        // ← 没有 let / const
```

经典脚本（非严格模式）里，"给一个没声明过的名字赋值"**不报错**，而是悄悄在 `window` 上建一个**全局变量**。于是有两种后果：

| 场景 | 结果 |
|---|---|
| 页面**第一次**调用就断流（全局还不存在，读它会抛错） | `ReferenceError: sawDone is not defined` |
| 之前**成功过一次**（全局已被置成 `true`） | **`sawDone` 永远是 `true`** → `!sawDone` 恒为 false → **这段检查形同不存在** |

实测（同一份代码、同一个假 `fetch`，只换执行顺序）：

```
先跑一次成功流        → 全局 sawDone 被置为 true
再跑"没有 [DONE]"的流 → 收到: 你 / 收到: 好 / ✅ 正常返回     ← onError 没被调用
把"没有 [DONE]"放第一个跑 → ReferenceError: sawDone is not defined
```

**所以正常测试永远发现不了它**：测的每一条正常流都在替它"上膛"。

**教训**：
> **忘了 `let` 在非严格模式下不报错，而是造一个全局变量 —— 而全局变量会「跨调用串味」。**
> 这类 bug 的症状是**偶发 + 静默**：跟"之前跑过什么"有关，跟"这次对不对"无关。
> 加 `"use strict"`（或 `<script type="module">`）会让这种赋值**直接报错**，反而更容易发现。

**怎么治**：状态变量声明在**函数内部**（`chat.js:30` 的 `let sawDone = false`），每次调用各有一份。

**怎么验证**：把异常路径**当第一条**跑，或者连着跑两条不同的流 —— **执行顺序本身就是变量**，只测正常路径等于没测。

### 2026-10-05 · 前端的 `onError` / `onDone` 不是可选项

**症状**：后端 10-04 刚补好的三条错误分支，在前端**完全没生效** —— 连不上时界面显示的是 `undefined`。

**根因**：前端解析回调只认"正文"：

```js
const data = JSON.parse(payload)
onChunk(data.content)      // 后端发的是 {"error": "无法连接模型服务"} → data.content 是 undefined
```

**三个缺口是同一类问题**（只测正常路径时一个都看不见）：

| # | 缺口 | 实测症状 |
|---|---|---|
| 1 | 后端的 `{"error": ...}` 事件被当成正文 | `onChunk` 收到 `undefined` → 界面渲染出 `undefined` |
| 2 | 流结束但**没收到 `[DONE]`** | `onDone` 和 `onError` **都不触发** → 界面永远卡在"正在输入" |
| 3 | 调用时少传 `onError` | HTTP 500 时 `TypeError: onError is not a function` |

**教训**：
> **「正常路径通了」≠「错误路径存在」。** 一个只会 `onChunk` 的前端，会把后端所有的错误处理都吃掉。
> 回调要**给默认值**（`onError=()=>{}` 或 `onError?.(...)`），不能假设调用方每次都传全。

**怎么治**：
- `if (data.error) { onError(data.error); return }`（`chat.js:39`）
- `let sawDone = false` + 循环后 `if (!sawDone) onError('连接提前中断（没收到 [DONE]）')`（`chat.js:30/51-53`）
- 参数默认值（`chat.js:18-19`）

**怎么验证（不用真断网）**：把 `fetch` 换成一个**假的 `Response`**，内容自己拼：

```js
globalThis.fetch = async () => new Response(new ReadableStream({
  start(c) { c.enqueue(new TextEncoder().encode('data: {"content":"你"}\n\n')); c.close(); }
}), { status: 200 });
```

→ 三分钟就能把「错误事件 / 断流 / HTTP 500」三条路径全测掉，**比 DevTools 断网可控**（想造哪种情况就造哪种）。

### 2026-10-04 · `try` 包错层级 = 死代码（**比不写更危险**）

**症状**：`/api/chat/stream` 里明明写了 `except httpx.TimeoutException` / `except httpx.RequestError`，但把上游地址换成死端口（`http://127.0.0.1:9`）一试 —— **控制台照样炸出完整一条 `httpx.ConnectError` 栈，curl 照样只给 `(18)`**，那两条 `except` 一行都没执行。

**根因**：`try:` 原来写在 `async with client.stream(...)` 的**里面**：

```python
async with httpx.AsyncClient(timeout=httpx.Timeout(30.0, read=None)) as client:
    async with client.stream("POST", url, ...) as r:   # ← 连接/发请求发生在这一行
        try:
            async for line in r.aiter_lines():          # ← try 只盖住了"读"这一段
                ...
        except httpx.TimeoutException: ...
        except httpx.RequestError: ...
```

"连不上 / DNS 挂 / 连接超时"这些异常是在 `client.stream(...)` 的 **`__aenter__`** 抛的 —— 也就是**发请求那一刻**，在 `try` 外面。等代码进到 `try` 里时，连接早就建好了。

更隐蔽的一层：`read=None` 之后**读超时被彻底关掉**了，`TimeoutException` 事实上只剩"连接超时"一种来源 → **那条分支永远进不去**。

**实测对照**（唯一变量 = `try:` 的位置，同一个死端口、同一个异常）：

| | `try` 在里面 | `try` 包住两个 `async with` |
|---|---|---|
| 控制台 | `httpx.ConnectError` 从生成器里冒出去（栈翻到 `stream_response`） | `[DeepSeek error] 网络错误：All connection attempts failed`（自己的 `print`） |
| curl | `curl: (18) transfer closed with outstanding read data remaining` | `data: {"error": "无法连接模型服务"}` → `data: [DONE]` → 正常回到提示符 |
| 前端会看到 | 连接突然断掉，没有任何解释 | 一条能解析的错误事件 |

**修法**：把 `try:` 提到两个 `async with` **外面**，`except` 跟着退到同层。里层那个管 JSON 解析的 `try`（`json.JSONDecodeError` / `KeyError` / `IndexError`）**留着** —— 那是另一类异常，两层各管各的。

**教训**：
> **`try` 必须包住「异常真正被抛出的那一层」。** 写在里面 = 只盖住了后半段。
> **写了 `except` ≠ 处理了。** 一个永远进不去的错误分支会给你"我已经处理好了"的错觉 —— **这比不写更危险**。

**怎么验证（不用等真实故障发生）**：

```powershell
# ① 死端口：立刻被拒绝 → 应该进 RequestError 分支
#    把上游 URL 临时改成 http://127.0.0.1:9/v1/chat/completions
curl.exe -N -X POST http://127.0.0.1:8000/api/chat/stream `
  -H "Content-Type: application/json" -d '{\"message\":\"hi\"}'
# 期望：data: {"error": "无法连接模型服务"} + data: [DONE]（而不是 curl: (18)）

# ② 黑洞地址：真的等超时 → 应该进 TimeoutException 分支
#    URL 换 http://10.255.255.1/v1/chat/completions，connect 压到 0.5s

# ③ 打桩：把 httpx.AsyncClient.stream 换成「一进 __aenter__ 就抛」的假实现
#    → 不联网、不花钱，三条分支全能验；"流中途断"（ReadError）只有打桩能造出来
```

### 2026-10-04 · 父子的 `except` 顺序：**子类必须写在前面**

**症状**：`except httpx.TimeoutException` 和 `except httpx.RequestError` 两条，谁先谁后有讲究。

**实测**：
```
issubclass(httpx.TimeoutException, httpx.RequestError) → True     ← 前者是子类
issubclass(httpx.ConnectError,     httpx.RequestError) → True
issubclass(httpx.ConnectError,     httpx.TimeoutException) → False
```

**教训**：
> **`except` 从上往下匹配，第一个命中的赢。** 子类写在后面 = 永远轮不到它，还会报出错误的消息。
> 正确顺序：`TimeoutException` → `RequestError`。反过来，连接超时会被报成"无法连接模型服务"。

**顺带确认**：这两个 `except` 都点名具体异常，**不会误吞 `CancelledError`**（它是 `BaseException` 的子类，不是 `Exception`）→ 取消语义没被破坏。

### 2026-10-03 · 变量遮蔽：报错行（246）和病根行（264）隔了 18 行

**症状**：`curl.exe -N` 打流式接口，只回一句 `curl: (18) transfer closed with outstanding read data remaining`。看起来像"流没写对 / 上游没流"。

**根因**：`gen()` 里第 264 行写了 `data = json.loads(json_str)`，而参数就叫 `data`（`async def chat_stream(data: chatRequest)`）。**Python 的作用域是编译期决定的**：只要函数体里**任何位置**给 `data` 赋过值，整个函数里 `data` 就是局部变量 —— 于是第 **246** 行 `data.message` 立刻 `UnboundLocalError`，**在还没发请求的时候就炸了**。

真栈只在 uvicorn 控制台里，curl 那边一个字都看不到：

```
File "E:\测试\FastAPItest\main.py", line 246, in gen
    {"role": "user", "content": data.message}
UnboundLocalError: cannot access local variable 'data' where it is not associated with a value
```

**为什么 curl 看不到真相**：`StreamingResponse` 是**响应头先发、再跑生成器**的。200 和 `content-type` 已经发出去了，生成器才抛异常 → starlette 掐掉连接、没有 chunked 结束块 → curl 只能报 `(18)`。

**教训**：
> **报错位置 ≠ 病根位置。** 差 18 行的那种，读报错行永远读不出来 —— 要去读「**这个函数里还给谁赋过值**」。
> **流式接口报错，第一现场是 uvicorn 的控制台，不是 curl。** 这是坑表第 5 条（"错误只能藏在流的内容里"）发生在自己这边的版本。

**怎么治**：解析结果别叫 `data`（叫 `chunk` / `payload`）。定义变量前先看这个函数里有没有同名参数。

### 2026-10-03 · 「流不流」一半取决于客户端怎么收

**症状**：`curl` 迟迟不出东西，或者一次全出来 → 第一反应是"后端没写对"。

**实测**：同一个 `/api/chat/stream`，同一份后端代码：
```
ASGI 直连的测试客户端：一次收到 1 个大块
curl.exe -N          ：收到 10 个块，一块一个 token
```

**根因**：**缓冲是客户端行为**。PowerShell 里 `curl` 是 `Invoke-WebRequest` 的别名，它会把响应读完再给你；ASGI 测试客户端也是一次性把响应交出来。`curl.exe -N`（`--no-buffer`）才是那个开关。

**教训**：
> **用会缓冲的客户端看到"没流"，什么也证明不了。** 判断"服务端到底流不流"，客户端本身必须是流式的。
> 客观判据（别靠肉眼）：`curl.exe -N -o NUL -w "首字节 %{time_starttransfer}s / 总计 %{time_total}s"` —— **`首字节 << 总计` = 真流**。

### 2026-10-03 · PowerShell 5.1 给 `curl.exe` 传 JSON：字面量行，变量不行

**症状**：同一条 `curl.exe` 命令，写成变量就收 422，写在命令行里就 200。

**实测**（用 `curl.exe --trace-ascii` 看**实际发出的字节**，不是猜）：

| 写法 | 实际发出的 body | |
|---|---|---|
| `-d '{\"message\":\"hi\"}'` | `{"message":"hi"}`（16 字节） | ✅ |
| `--data-raw '{\"message\":\"hi\"}'` | `{"message":"hi"}`（16 字节） | ✅ |
| `$body = '{"message":"hi"}'` 然后 `-d $body` | `{message:hi}`（**12 字节**） | ❌ 引号被吃掉 |
| 同上，`--data-raw $body` | `{message:hi}`（12 字节） | ❌ |

**根因**：跟 `-d` / `--data-raw` **无关**（两种表现完全一样），差别在 **「字面量 vs 变量」** —— PS 5.1 把变量里的引号传给原生命令时会丢。用变量时后端收到的是 `{message:hi}`，直接 422，**看起来像接口写错了**。

**教训**：
> **想确认命令行工具到底收到了什么，用它自己的 trace（`curl --trace-ascii`），不要推断。**
> 给原生命令传 JSON：**把 `\"` 转义直接写在命令里**；非要用变量，就写进文件再 `-d "@body.json"`。

### 2026-10-01 · `flex-wrap` 的换行判断不看 `flex-basis`，看 `min-width`

**症状**：给 `header .box` 加上 `flex-wrap: wrap`，两张卡片写 `flex: 1 1 600px` / `flex: 1 1 380px`，本来期望"够宽就并排、窄了才换行"。结果**桌面端 1080px 宽的时候也换行了** —— content1 和 content2 变成上下两行，各自撑满 1080。

**根因**：flex 子项的 `min-width` 默认是 **`auto`**，含义是"**不能小于我的内容最小宽度**"；而 **`flex-wrap` 的换行判断用的是被 `min-width` 夹过之后的值**，跟 `flex-basis` 里写的 600/380 没有关系。而卡片里还留着写死的宽度：

```
content1 的内容最小宽度 = 内层 .column1/.column2 的 576 + padding 64 = 640
content2 的内容最小宽度 = 内层 .timeline 的 376      + padding 64 ≈ 454
640 + 454 + 20(gap) = 1114  >  1080  →  一行放不下  →  换行
```

**教训**：
> **`flex: 1 1 <理想宽度>` 和 `min-width: 0` 是一对，不能只写前半个。**
> 更一般的：**写死的内层宽度会以「内容最小宽度」的形式，隔着两层把外层的并排布局顶穿。**

**怎么治**：
```css
header .box .content1,
header .box .content2{ min-width: 0; }
```
⚠️ 但 `min-width: 0` 只是"**允许**压得比内容还窄"—— 里面若还有写死宽度（`.timeline` 376），压窄后就会**顶出卡片**。所以它必须和"放开内层固定宽度"一起做（方法见 [布局地图.md](布局地图.md) 第四节的三分类）。

### 2026-10-01 · `flex-basis` 是「主轴尺寸」：主轴一翻转，`600px` 从「宽」变成「高」

**症状**：手机上（768）content1 特别"空" —— 内容都贴在卡片的上下两头，中间一大片空白，卡片高得离谱。第一反应是"`height:auto` 被内容撑开了吧"，**恰恰相反**。

**根因**：基准层写的是
```css
header .box .content1{ flex: 1 1 600px; }
```
断点层又写
```css
@media (max-width: 768px){ header .box{ flex-direction: column; } }
```
**主轴翻成纵向之后，`flex-basis: 600px` 被解释成「高 600px」**（`flex:` 里的尺寸永远是**主轴**尺寸）。`.box{height:auto}` 也救不回来 —— auto 高的容器没有"负剩余空间"可分配，子项就按 flex-basis 取高。再叠加 `.content1` 自己的 `justify-content: space-between`（css:127），两块内容被顶到上下两头 → 中间空出「600px 减内容高度」的空白。

**验证方法（量化，很好用，别用眼睛猜）**：在 DevTools 里量卡片的实际高度，再除以 DPR：
```
content1 实测 ≈ 899 真实 px ÷ DPR 1.5 = 600 CSS px   ← 精确等于 flex-basis 里的 600
```

**教训**：
> **`flex:` 里那个尺寸是主轴尺寸，方向一变含义就变。**
> 凡是「基准层横排、断点里改竖排」的地方，都要在断点里**顺手重置 flex**。

**怎么治**：
```css
@media (max-width: 768px){
    header .box .content1,
    header .box .content2{ flex: 0 0 auto; }   /* = flex:none，高度交还给内容 */
}
```

### 2026-09-29 · git 的「后悔药」对未跟踪文件无效

**症状**：以为「改坏了就 `git checkout --`」，但那两个最值钱的文件救不回来。

**实测**：
```powershell
git status --short --untracked-files=all
#  D DB_PATH
#  M main.py            ← 已改未提交
#  M models.py          ← 已改未提交
# ?? dependencies.py     ← 完全未跟踪
# ?? security.py         ← 完全未跟踪
# ?? static/login.html   ← 完全未跟踪
```

**根因**：
- `??` = **git 根本不知道这个文件存在**，所以没有任何历史版本可回退
- `M` = 改了但没 commit，`git checkout --` 只会退回**上一个 commit**，不是「刚才好的样子」
- 整个仓库只有 **1 个 commit** → 兜底能力约等于零

**教训**：
> **`git checkout --` 只对「已提交过的文件」有效。**
> 判断方法：看 `git status` 第一列。`??` 的文件没有任何后悔药。

**怎么治**：写完一个新文件就 commit，别攒。见 [下一步计划.md](下一步计划.md)。

### 2026-09-29 · `.env` 到底被哪条规则忽略？

**为什么疑**：`.gitignore` 里写了 `.env`，但不确定它是否真的生效。

**怎么验证（一行命令，别猜）**：
```powershell
git check-ignore -v .env
# .gitignore:2:.env    .env      ← 有输出 = 规则生效

**结果**：✅ 生效。`.env` 不会被 `git add .` 带走。

> **`.gitignore` 写了 ≠ 生效**（可能被后续规则覆盖、可能路径写法不对）。

### 2026-09-13 · `file://` 打开页面导致 fetch 路径「看起来」写错了

**症状**：`fetch('/api/profile')` 报 `file:///E:/api/profile`，看起来像相对路径写错了。

**根因**：页面被**双击**用 `file://` 打开，而不是通过服务器访问。同一个路径在两种打开方式下指向完全不同的地方。

**正解**：通过服务器访问页面（`http://127.0.0.1:8000/static/`），`/api/profile` 本身就是对的。

**错解**：改成写死 `http://127.0.0.1:8000/api/profile` —— 部署后会指向**用户自己的电脑**，而且同源变跨域，CORS 问题会重新冒出来。

**教训**：
> **报错指向的位置，不一定是问题所在。** 先分清「代码错」还是「环境错」。

## 阶段 2 踩的坑（重名覆盖 / 工具切换）

### 重名覆盖 —— 同一周撞了 3 次

| # | 症状 | 根因 |
|---|---|---|
| 1 | SQLAlchemy 报「找不到映射」 | `class User(BaseModel)` **覆盖了** `models.User` |
| 2 | 行为诡异但**不报错** | 两个 `UserOut` 同时存在（第 22 行 / 第 50 行），**后定义的静默赢** |
| 3 | 会话表相关全乱 | `class Session` 覆盖了 `sqlalchemy.orm.Session` |

**教训**：
> **Python 对重名完全不管：后定义的静默赢，不报错、不警告。**
> 习惯：定义一个名字之前先想「这个名字有没有被用过」。
> Pydantic 模型加后缀：`UserOut` / `UserCreate`；会话表叫 `SessionToken`。

### 换工具时，以前手动做的事会「悄悄丢」

| 以前手动做的 | 换成 SQLAlchemy 后 |
|---|---|
| `PRAGMA foreign_keys=ON` | **没了** —— 外键约束形同虚设（`user_id=999` 居然插得进去） |
| `CREATE TABLE` 建表 | `create_all()` **只管不存在的表**，不给已有表加字段 |

**这类「隐形的能力丢失」没有症状**：程序照跑，只是不再拦坏数据了。

**教训**：
> **换工具时问一句：「之前我手动做的那件事，新工具替我做吗？」**

### 其他零散坑

| # | 症状 | 根因 / 教训 |
|---|---|---|
| 1 | `session.scalar()` 取不到对象 | **`scalar` 取单个值（聚合用），`scalars` 取对象列表**，再 `.first()` |
| 2 | `User.password_hash` 报错 | **类没有数据，实例（查出来的 `user`）才有** |
| 3 | `server_default=0` → `ArgumentError` | 要**字符串或 `text(...)`**：`text("0")` |
| 4 | `does not have a __table__ or __tablename__` | 忘了写 `__tablename__` |
| 5 | 漏括号 | `with SessionLocal as session:` → **`SessionLocal` 是工厂，必须调用** |
| 6 | 多写了一对括号 | `with SessionLocal() as session():` → `SyntaxError` |
| 7 | `response_model=PostOut` 但返回列表 → 500 | 要 `list[PostOut]` |
| 8 | Pydantic 读不了对象属性 | 忘了 `model_config = ConfigDict(from_attributes=True)` |
| 9 | `if not user_id:` 判断错了对象 | **要判断【查出来的结果】，不是【传进来的参数】**。传 999（不存在）时判断失效 → `NoneType` 崩溃 |
| 10 | `ph.verify()` 参数顺序 | 原生是 `verify(hashed, password)`。**包装成 `verify_password(password, hashed)` 更符合直觉** |
| 11 | 旧数据 `hash123` 让验证崩溃 | 它**不是合法的 argon2 哈希** → 抛 `InvalidHashError`（不是 `VerifyMismatchError`）。**真实系统里就是有脏数据** |
| 12 | `except` 里忘了 `return` | 声明返回 `bool`，实际返回 `None` |
| 13 | `return {"删除成功"}` | **`{x}` 是集合（set），`{"k": v}` 才是字典**。FastAPI 会编码成 `["删除成功"]` |
| 14 | Swagger 里看不到 `Set-Cookie` | **它在浏览器「禁止 JS 读取」的名单里**。用 DevTools → Application → Cookies |
| 15 | `git diff` 掉进分页器 | 按 `q` 退出 |
| 16 | 在用户主目录误 `git init` | 会让那个目录下**所有子目录**都被接管。查「谁在管我」：`git rev-parse --show-toplevel` |

```
