**卡在哪（一开始不懂 → 后来明白）**：

1. **链式依赖到底在链什么**：一开始就是想给 main 的流式接口加限流检测依赖，再在限流依赖函数那里写鉴权依赖 —— 依照"先认证你是谁，再给你这个用户应有的权力"。这就是我理解的鉴权：**先鉴权才知道你是谁，然后才能检查你干了什么、有没有超权、要不要限流**，这就是链式依赖。
2. **为什么不用列表存时间戳**：一开始想用"字典 + 数组(列表)"存用户记录，后来才知道用数组效率极慢 —— 改一个时间戳要改后面所有的时间戳，是 O(n) 的长度。用**双端队列**队首删、队尾加效率很高，只需要删掉两个指针、释放内存。
3. **固定窗口 vs 滑动窗口**：一开始不理解两者的区别，后面通过例子才明白 —— 是"整点清零"和"最近 N 秒内"的区别。
4. **`while history and ...` 里的 `history` 不能省**：一开始不知道为什么要判断它是否存在，后来查了才知道 —— 不判断的话，`history` 为空时 `history[0]` 会直接报 `IndexError`。
5. **差 1 那个坎**：我一直觉得"队列长度 > 上限就是超额"，怎么也想不到为什么要 `>=`。
   根因：**那个直觉只在「先记后查」的结构下成立**，而我写的是「先查后记」—— **检查的时候，"这次"还没进队列**，所以 `len(history)` 是"已经放行的次数"，不含本次。
6. **验收差点变成"假通过"**：搜 `sk-` 无结果，但"搜不到"有两种可能 —— **真没泄漏** vs **搜法不对**（假阴性）。补了**正向对照**（先搜一个一定存在的 `content`，确认搜索真的在工作）之后，结论才立得住。**一个永远会通过的测试，等于没测。**

**今天最大的认知更新**：

- **`yield` 依赖的清理时机 = 最后一块产出之后**（实测时间线：`+0.61s 最后一块` → `+0.91s 依赖 exit`），**不是函数返回时** → 所以它能拿来当并发槽

```

**那两条 `except` 一行都没执行。**

根因：`try:` 原来写在 `async with client.stream(...)` 的**里面**，而"连不上 / 连接超时"是在 `client.stream(...)` 的 `__aenter__` 抛的（**发请求那一刻**），在 `try` 外面。再加上 `read=None` 之后读超时被关掉了，`TimeoutException` 事实上只剩"连接超时"一种来源 → 那条分支永远进不去。

**修法**：`try:` 提到两个 `async with` 外面（`main.py:240`），`except` 退到同层。改完再打同一个死端口：

```
data: {"error": "无法连接模型服务"}
data: [DONE]
```
控制台 `[DeepSeek error] 网络错误：All connection attempts failed` + `200 OK`。**同一个异常，只改一行位置，行为从"崩"变成"报错"。**

**另外三条分支用打桩全验掉了**（把 `httpx.AsyncClient.stream` 换成"一进 `__aenter__` 就抛"的假实现 —— 不联网、不花钱）：

| 打桩抛出 | 实际输出 | 分支 |
|---|---|---|
| `ConnectTimeout` | `data: {"error": "模型服务响应超时"}` + `[DONE]` | `:271` ✅ |
| `ConnectError` | `无法连接模型服务` + 控制台 `print` | `:274` ✅ |
| `ReadError`（**流中途断**，死端口造不出来） | 同上 | `:274` ✅ |

**顺带一条**：`TimeoutException` 和 `RequestError` 的**顺序有讲究** —— 实测 `issubclass(httpx.TimeoutException, httpx.RequestError) == True`（前者是后者的**子类**），所以**子类必须写前面**，否则连接超时会被报成"无法连接模型服务"。

**今天最大的认知更新：写了 `except` ≠ 处理了**

一个永远进不去的错误分支，会给你"我已经处理好了"的错觉 —— **这比不写更危险**，因为它让你在真出事时不去查那里。判据只有一个：**让它真的抛一次，看错误事件有没有出来**。
