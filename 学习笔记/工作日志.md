我把上游 URL 换成死端口 `http://127.0.0.1:9/v1/chat/completions` 一试：

```
httpx.ConnectError: All connection attempts failed     ← 从生成器里冒出去，栈翻到 uvicorn
curl: (18) transfer closed with outstanding read data remaining
```

**那两条 `except` 一行都没执行。**

根因：`try:` 原来写在 `async with client.stream(...)` 的**里面**，而"连不上 / 连接超时"是在 `client.stream(...)` 的 `__aenter__` 抛的（**发请求那一刻**），在 `try` 外面。再加上 `read=None` 之后读超时被关掉了，`TimeoutException` 事实上只剩"连接超时"一种来源 → 那条分支永远进不去。

**修法**：`try:` 提到两个 `async with` 外面（`main.py:240`），`except` 退到同层。改完再打同一个死端口：

```
data: {"error": "无法连接模型服务"}
data: [DONE]
```
控制台 `[DeepSeek error] 网络错误：All connection attempts failed` + `200 OK`。**同一个异常，只改一行位置，行为从"崩"变成"报错"。**

**另外三条分支用打桩全验掉了**（把 `httpx.AsyncClient.stream` 换成"一进 `__aenter__` 就抛"的假实现 —— 不联网、不花钱）：

| 打桩抛出 | 实际输出 | 分支 |
|---|---|---|
| `ConnectTimeout` | `data: {"error": "模型服务响应超时"}` + `[DONE]` | `:271` ✅ |
| `ConnectError` | `无法连接模型服务` + 控制台 `print` | `:274` ✅ |
| `ReadError`（**流中途断**，死端口造不出来） | 同上 | `:274` ✅ |

**顺带一条**：`TimeoutException` 和 `RequestError` 的**顺序有讲究** —— 实测 `issubclass(httpx.TimeoutException, httpx.RequestError) == True`（前者是后者的**子类**），所以**子类必须写前面**，否则连接超时会被报成"无法连接模型服务"。

**今天最大的认知更新：写了 `except` ≠ 处理了**

一个永远进不去的错误分支，会给你"我已经处理好了"的错觉 —— **这比不写更危险**，因为它让你在真出事时不去查那里。判据只有一个：**让它真的抛一次，看错误事件有没有出来**。

**踩到的坑**：

1. **`UnboundLocalError`：报错行（246）和病根行（264）隔了 18 行**
   循环里写了 `data = json.loads(json_str)`，把路由函数的参数 `data` 遮蔽了。Python 只要在函数体里对某个名字**赋值**，整个函数里它就是局部变量 —— 所以第 246 行的 `data.message` 先炸，而报错的那一行看起来毫无问题。改名 `chunk` 就通了。
2. **`curl: (18) transfer closed with outstanding read data remaining` 只说明"连接断了"**
   200 和响应头已经发出去了，真正的栈**只在 uvicorn 那个终端里**。→ 流式接口排错第一条：先看 uvicorn 控制台，别盯着 curl 的输出找。
3. **改完立刻 curl 会打到旧代码**
   uvicorn `--reload` 有重启延迟。要等控制台打完 `Application startup complete.` 再 curl，否则会看到"还是 (18)"，白怀疑一遍代码。

**今天最大的认知更新：同一个后端，"流不流"一半取决于客户端怎么收**

同一个接口，ASGI 直连的测试客户端一次只收到 **1 个大块**，而同一时刻 `curl.exe -N` 收到 **10 个块**。所以坑表第 4 条（PowerShell 的 `curl` 是 `Invoke-WebRequest` 的别名、会把响应缓冲完）的真正含义不是"后端没流"，而是**客户端在缓冲**。

顺带实测掉两条**预判**：

- **`\uXXXX` 不是乱码**：`json.dumps` 默认 `ensure_ascii=True`，中文被转义成 `\u4e00` 这种；浏览器 `JSON.parse` 会自动还原 → **两种都行**（10-04 补：后来在 `content` 那行加了 `ensure_ascii=False`，curl 里能直接看中文；代价是响应不再是纯 ASCII，老的 GBK 终端会花屏）
- **上游第一块 `content` 是空串**（不是"没有 content"）→ "`delta["content"]` 会 KeyError"这条预判**不成立**；真正要防的是**把空串当结束**（会在第一个 chunk 就退出，表现成"一个字都没有"）

**今天最大的认知更新：断点 ≠ 响应式**

我一开始写的断点里全是**按 375 算出来的死值**（8px 导航字号、15px padding、`20%/80%` 头像分配），换个宽度就废 —— 那不是响应式，是"375 专用补丁"。真正的做法是**流动布局兜底 + 少量结构切换断点**：先把写死的尺寸换成 `max-width` 和 `flex: 1 1 <理想宽度>`，只在结构必须变的地方补一两刀。按这个思路，这一页真需要的断点只有 **2 个**。

顺带发现一个自己从来没意识到的洞：`max-width:768` 只管到 768，而基准样式是给 1080 配的 → **769–1080px 完全没人管**，把窗口拖到 900px 就横向滚动。

**踩到的三个坑**（都是「写死的东西从想不到的地方咬你」，详见 [踩坑记录.md](踩坑记录.md)）：

1. `flex: 1 1 600px` 少了半句 `min-width: 0` → 桌面端两张卡片从并排变成上下两行

3. 内层写死的宽度会以「内容最小宽度」的形式，**隔着两层**把外层的布局顶穿
