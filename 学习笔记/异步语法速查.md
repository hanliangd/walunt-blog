## 一、三个东西其实是三套协议

| 语法 | 走的协议 | 涉及的方法 | 各方法要不要 `await` |
|---|---|---|---|
| `await x` | 可等待对象协议 | `__await__` | 它本身就是 await |
| `async with x as y` | **异步上下文管理器** | `__aenter__` / `__aexit__` | **两个都要**（语法代劳） |
| `async for x in y` | **异步迭代** | `__aiter__` / `__anext__` | `__aiter__` **不要**；`__anext__` **要** |

> ⚠️ `async with` 和 `async for` 是**两套不同的协议**，不是"同一个协议的两种写法"。
> 直觉上把它们当成"都藏着 await 的语法糖"没问题，**但术语别混** —— 这是最容易被 AI 讲错的地方。

实测（同一个对象同时实现两套协议，看语法各调谁）：

```
async with Both():        → __aenter__ / __aexit__
async for x in Both():    → __aiter__  / __anext__
```

而且 `httpx` 的 `client.stream(...)` 产物实测是：

```
类型: contextlib._AsyncGeneratorContextManager
有 __aenter__/__aexit__ : True True
有 __aiter__/__anext__ : False False
```

—— 它**根本不是"异步可迭代"**，只是异步上下文管理器。

另外：`async with` / `async for` **只能出现在 `async def` 里**，写在同步函数里是 `SyntaxError`。

## 二、`async with` 的忠实展开

```python
mgr = EXPR
value = await mgr.__aenter__()
try:
    BODY
except BaseException:
    if not await mgr.__aexit__(*sys.exc_info()):
        raise                          # ← __aexit__ 返回假值 → 异常继续往上抛
else:
    await mgr.__aexit__(None, None, None)
```

**三个关键点，全是实测过的：**

1. **`__aenter__` 必须是 `async def`。** 写成普通 `def` 返回非 awaitable 对象，Python 直接报：
   ```
   TypeError: 'async with' received an object from __aenter__ that does not implement __await__
   ```
   → 这就是"语法内部藏着 await"的**直接证据**。

2. **出异常时 `__aexit__` 收到的是真实的 `(type, value, traceback)`**，不是 `(None, None, None)`。

3. **`__aexit__` 返回真值 → 异常被吞掉。** 这是它和 `try/finally` 的**关键区别**（`finally` 不吞异常）。

实测：
```
__aexit__ 返回 True：  收到 ValueError / boom → raise 之后那行执行了（异常被吞）
__aexit__ 返回 False： 收到 ValueError        → 异常照常抛出
```

## 三、`async for` 的忠实展开

```python
it = EXPR.__aiter__()          # ← 不 await！（3.7+ 起必须是普通函数，直接返回异步迭代器）
while True:
    try:
        x = await it.__anext__()
    except StopAsyncIteration:
        break
    BODY
```

- `__aiter__` 写成 `async def` → `TypeError: 'async for' received an object from __aiter__ that does not implement __anext__: coroutine`
- **异步生成器函数天然满足这两个协议**（`__aiter__` 返回自身），所以 `r.aiter_lines()` 能直接 `async for`。
- **`__aiter__` 是唯一一个「不该 await」的** —— 所以"所有 await 都在、只是被语法糖藏起来了"这句话对它不成立。

## 四、这几条说法，实测判定

| 说法 | 判定 |
|---|---|
| "`async with` 和 `async for` 是同一个协议" | ❌ 两套 dunder，实测各调各的 |
| "`async with` 等价于 `try/finally`" | ⚠️ 结构像，但**吞异常的语义不同** |
| "所有 await 都被语法糖藏起来了" | ⚠️ 对 `__aiter__` 不成立 |
| "那张展开图可以直接照着写代码" | ❌ 它是**心智模型**，不是可运行代码（`__aenter__` 要绑实例、`stream(...)` 得先调用才拿到上下文管理器） |
| "语法内部自己 await，不用你手写" | ✅ 对（`__aenter__` 那个报错就是证据） |

## 五、和本项目的关系（为什么这几条在这里特别值钱）

1. **`gen()` 是异步生成器函数：调用它，一行都不执行。**
   `main.py:348` 的 `return StreamingResponse(gen(), ...)` 执行完时，两个 `async with` **都还没进入** —— 它们发生在 Starlette **第一次迭代响应体**（第一次 `__anext__`）的时候。
   → 所以 `main.py:296` 的 `if not Mykey: raise HTTPException(500, ...)` 写在**生成器外面**是对的；挪进去就变成 200 + 流内错误。
2. **认证放 `Depends` 而不是生成器里**，同一个道理：`Depends` 在函数体之前跑完，401 是一个**完整的 HTTP 响应**（实测：`HTTP 401` + `content-type: application/json` + `{"detail":"未登录"}`），**生成器压根没被调用** → 前端 `res.status !== 200` 能干净接住。放进生成器的话，401 只能混进 SSE 流里，前端拿到的是 200。
3. **`try:` 必须包住两个 `async with`**（`main.py:300`）：连接阶段的异常是在 `client.stream(...)` 的 **`__aenter__`** 抛的，写在里面就接不住（10-04 那个坑）。
4. **客户端断开时上游连接会被自动关**：`async with` 的 `__aexit__` 在生成器被关闭/取消时同样会执行 —— 这就是"`CancelledError` 不用额外处理"的理由之一。
